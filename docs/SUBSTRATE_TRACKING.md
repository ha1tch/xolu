## 3. Verification discipline — how to keep this table honest

This table exists because a single-source status check produced a
materially wrong answer once already (Wave 2 reported as 0% when it was
genuinely ~50%, in the same session that built this file). The error
had a precise, reproducible cause: **trusting one document's header
without reading its body, and without cross-checking a second
independent source.** The correct procedure is not "be more careful" —
it is a fixed order of checks, because each source has a specific blind
spot the next source in the order catches.

**Never trust a single source. Check in this order, and don't stop
early just because the first source gives an answer:**

1. **Code, directly.** For any claim about width, type, or existence
   ("tenant ID is uint32", "the client library exists") — grep or read
   the actual source. A package existing (`pkg/refintegrity`) is not
   evidence of what stage its contents implement; read the files.
2. **`CHANGELOG.md`, for explicit item/wave tags.** This project tags
   releases with `(item N, wave M)` and occasionally an explicit **"WAVE
   N COMPLETE"** string (wave 3's v0.16.10 entry is the clean example).
   These are the highest-confidence source when present — search for
   `item N\b`, not just prose keywords, since the same feature is
   described differently release to release.
3. **`docs/RESOLVED.md`, by T-id, not by prose phrase.** Grepping for a
   feature's plain-English name ("referential integrity") is exactly
   what failed this session — the closure was filed under `T-48` /
   `G-12` / `XOLU-RI00x`. Once you have candidate T-ids from step 2,
   confirm each one closes here. Don't search RESOLVED.md by vocabulary
   alone.
4. **`docs/KNOWN_ISSUES.md`.** This is where recorded decisions, stage
   boundaries, and dormant-guard verification records live — and it was
   the single document skipped that caused this session's Wave 2 error.
   Any wave with staged or partial delivery (RI is the current example)
   has its real boundary documented here, not in the register.
5. **The proposal or plan document itself — read the whole thing, not
   just the header.** A design document's status line can go stale the
   moment its body is updated without the header following along
   (`referential-integrity.md` is the live example: header says
   "scheduled", §8 says "done"). The body's own staging/acceptance
   table is authoritative over its own header.
6. **`register.py list` / `TRACKING.md`, for what's still open.** This
   catches items that were *never* filed at all — which is a different
   failure from "filed but not yet closed." Item 8 (wave 1) is the
   example: it appears in none of the above, closed or open, and that
   absence is itself the finding. Absence of a register entry is not
   evidence of completion; check the code (step 1) before concluding
   either way.

**A single source answering confidently is not a stopping condition.**
The proposal header alone answered "scheduled" clearly and wrongly.
Only cross-checking against KNOWN_ISSUES.md and CHANGELOG.md surfaced
that the body disagreed with the header it was attached to. Treat
agreement across at least two independent sources (not two mentions in
the same document) as the bar for marking a wave item ✓ in this table.

**A second, distinct failure mode: the plan's own item *labels* can
mismatch what the item actually does.** Item 8's inventory-table row is
titled "Tenant ID → uint32" — but the plan's own §1 rationale (a
different section, easy to skip when the table row already looks
self-explanatory) states plainly that the tenant identifier stays
